### Bug fix

**You own this task. Plan, review, verify.** Scale investigation, design, and coordination to the defect; preserve reproduction and final review.

For a UI action whose result is reset or changes with timing, use [click-path tracing](../../how/references/click-path-audit.md) to follow the composed handler and its final state before choosing the regression check.

Be scientific. Every shipped line traces to runtime evidence. Belt-and-suspenders that "might help" is a hypothesis, not a fix; it does not ship. When evidence refutes a hypothesis, revert what it motivated. The smallest change the evidence justifies ships, nothing more. Same discipline for Perf, where the evidence is the trace.

1. Reproduce it on a safe local, test, or otherwise authorized surface with the host's available browser, PTY, simulator, or application-control capability. Never synthesize triggers or add instrumentation against production or third-party systems without explicit authorization. If the host cannot reach the target, state the exact limitation and ask for the smallest missing artifact or user-run step. A bug you cannot reproduce cannot be proved fixed.
2. Trace the reproduced failure to its cause. Inspect and test a clear local path directly. Use `$deepwright:how` when the affected subsystem or call path needs investigation, and `$deepwright:why` when regression history could distinguish causes or reveal a compatibility constraint. When hypotheses compete, choose the next observation that rules out alternatives. When program state is unclear, add scoped instrumentation or logging and read it as the code runs. Confirm the mechanism with runtime evidence before designing the fix. For a long hunt, iterate in bounded passes and checkpoint under `.deepwright/runs/<run-slug>/`; do not assume a persistent background command exists.
3. Plan the smallest fix justified by the evidence. Invoke `$deepwright:architect` when the fix changes a consequential interface, ownership boundary, or data model, or leaves an unresolved design tradeoff. Choose the regression check with `$deepwright:tdd` before editing production behavior; its practical fallback rules apply to unit and integration checks alike. Implement directly when coordination would add more overhead than value. Delegate only when collaboration is available and an independently scoped investigation or implementation would help; give the worker the evidence, acceptance criteria, and authorization limits, then review its result. Otherwise work sequentially. Never hard-code a provider or model name.
4. Verify on the same surface; the original repro now passes. "Inconclusive" or wrong-surface is not a pass; flag it. Unit tests show branch behavior, not bug absence.

   If overlapping work can publish to shared or visible state, also trace each operation from input capture through completion to publication. Use an existing seam to hold an older operation, let a relevant newer state change complete, then release the older operation. Check the current state and a subsequent consumer against the affected contract. A result can remain valid for its original caller yet no longer be valid to publish; intentional cancellation is not itself a failure. Exercise only a completion order that could violate the contract, without adding scheduling machinery to unrelated fixes.
5. Review the final diff against the intended behavior, compatibility constraints, and authorized scope. A separate local review pass is sufficient for a small, low-risk fix. When independent review is requested or warranted by the risk, use an available read-only reviewer; disclose a sequential fallback when independent review is unavailable.
6. When commits are authorized, preserve the failing-before and passing-after evidence and shape the change into small, ordered commits under `$deepwright:principle-sequence-verifiable-units`. A request for a local fix does not itself authorize commits. Do not skip the regression check merely because it is an integration test, or fabricate a failure to make the history tell a better story.
7. Run **Opening a PR** only when the user asked for a PR or the authorized workflow explicitly includes one.

**Reply:** what was broken, root cause, fix, and how you verified it. Include a minimal redacted failing-then-passing excerpt or point to a local receipt; never paste secrets, tokens, personal data, or an unnecessarily large log.

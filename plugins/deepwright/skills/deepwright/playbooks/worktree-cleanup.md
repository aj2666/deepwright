### Worktree and simulator cleanup

**You own the audit, not permission to delete.** Reclaim space only from exact targets the user approves after seeing the evidence. Worktrees, simulators, caches, and application state are separate scopes; approval for one never authorizes another.

1. **Resolve the audit root.** Verify the repository path without using broad targets such as `/`, `~`, or an unresolved environment variable. Record filesystem usage for the relevant volume and write the audit to `.deepwright/runs/<run-slug>/cleanup.tsv`.
2. **Enumerate worktrees read-only.** Use `git worktree list --porcelain` so paths with spaces remain exact. For each path, record branch, HEAD, disk use, tracked and untracked changes, whether it is the current worktree, whether the branch is merged into the resolved default branch, and open PR state from the available GitHub connector or authenticated `gh`. Do not fetch, prune, delete, or scan private host application data during the audit.
3. **Verify current use from supported evidence.** Hold the current worktree, any path named by the user as active, paths used by live processes you can safely identify, and every worktree with uncommitted or untracked files. Do not infer activity from hidden transcripts or unrelated conversations. When doubt remains, mark `needs-user-decision`.
4. **Present exact candidates and wait.** Show canonical paths, estimated bytes, branch and commit, merge/PR state, and every uncommitted filename. Ask the user to approve the exact deletion list. Clean and merged is evidence, not permission. Never treat untracked files as disposable by default.
5. **Remove only the approved clean set.** Revalidate each canonical path and its status immediately before removal. Use `git worktree remove <exact-path>` without `--force`. Then run `git worktree prune --dry-run`; prune only when every reported metadata entry belongs to the approved set, otherwise show the extra entries and ask. If removal fails because data remains, stop and report it. Do not fall back to raw recursive filesystem deletion. A forced removal or deletion of any uncommitted content requires a separate explicit approval and a recoverable backup chosen by the user.
6. **Handle simulators and caches as separate opt-ins.** First list exact simulator devices, runtimes, DerivedData entries, DeviceSupport entries, and package-cache directories with sizes. Ask for the exact set to remove. Prefer supported per-item deletion or a recoverable trash operation. Never delete all simulators, all runtimes, host application state, Library folders, or broad caches from a generic cleanup request.
7. **Verify outcome.** Re-list worktrees and filesystem usage, then record the removed targets and observed space delta. If the delta differs from estimates, report it without deleting more.

**Reply:** before and after usage, exact targets removed, whether each removal is recoverable, targets held back and why, and the cleanup-ledger path.

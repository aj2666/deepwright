### Shipping

**You own what lands. Verify each PR independently and merge only the exact set the user authorized.** Use only for an explicit request such as "merge PR 42", "land this named stack", or "enable merge when ready for these PRs". An ambiguous "ship it" requires resolving the repository and PR set before any merge.

This follows `playbooks/babysit.md`. Babysit makes a PR merge-ready; Shipping decides whether the current patch is safe and performs the authorized merge action.

1. **Resolve authority and GitHub access.** Record the exact repository, account, PR list, order, merge method, and whether auto-merge is authorized. Prefer the available GitHub connector; otherwise use authenticated `gh`. Verify target visibility, base branch, head branch, and current user before the first write. A clean verdict is a safety gate, not authorization.
2. **Verify every PR independently.** Use a reviewer that did not author the patch. Invoke `$swarm` when available; otherwise run an independent gates, diff, and live-behavior review with the host's available browser, terminal, simulator, or application-control capabilities. Each verdict is `PASS`, `PASS+NOTES`, `FAIL`, or `BLOCKED`, tied to repository, PR, base SHA, head SHA, and stable patch ID. CI green or an approving bot is not a verdict. Store the record in `.deepwright/runs/<run-slug>/verdicts.tsv`; posting it to GitHub requires comment-write authorization.
3. **Find the contiguous verified run.** Walk from the lowest unmerged PR upward and stop at the first `FAIL`, `BLOCKED`, or missing verdict. A verified child above a gap is not landable because its diff includes the parent chain.
4. **Re-check the patch.** Before each merge, compare the recorded base SHA, head SHA, and stable patch ID with current GitHub and git state. Re-verify any changed patch. If only the SHA changed and the patch ID did not, retain the code verdict but re-run required checks and mergeability.
5. **Do not rewrite topology implicitly.** Fetch the resolved default branch and inspect only the bottom PR. If landing requires a rebase, base retarget, or force-push, pause unless the user's request explicitly authorized that operation on that exact branch. Prefer asking the stack owner to restack. Re-run step 4 after any authorized rewrite.
6. **Land one PR at a time.** Use the selected GitHub backend and the authorized merge method. With `gh`, a squash merge is `gh pr merge <pr> --squash`. Use `--auto` only when the user explicitly requested merge-when-ready. Re-read the PR immediately after the call; never infer success from command submission alone.
7. **Recompute after each merge.** Confirm the PR is merged and the default branch contains the result. Remove it from the frozen bottom-to-top list, then inspect the new bottom PR's base, head, checks, reviews, and patch ID. Do not assume GitHub retargeted descendants correctly.
8. **Wait only within host limits.** Use the available GitHub connector or a bounded `gh pr checks --watch` during the active turn. If the PR remains queued when the session must end, checkpoint the exact state and next query in `.deepwright/runs/<run-slug>/resume.md`; do not mutate descendants around it.
9. **Stop at the authorized ceiling.** Do not extend the set because another PR happens to be green. Report what landed, what remains, and what additional authorization or verification is needed.

**Reply:** the authorized and verified run, base/head/patch ID per PR, the backend and merge method used, what auto-merge was armed, what actually landed, the next gap, and the run-ledger path.

### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue, then hand the user one linear base-branch stack to review and land.** Use for "stack them, do not ship" or dependent PR work where merge authority is withheld.

1. **Resolve scope and GitHub access.** A request to state the plan is not permission to execute it. On explicit go, record the named work items and allowed branch and PR writes. Prefer the available GitHub connector; otherwise use authenticated `gh` after verifying repository and account. If neither can write, prepare local branches and report the blocked operation.
2. **Create `.deepwright/runs/<run-slug>/`.** Record the objective, default branch, intended parent for every PR, owner, state, head SHA, verdict, decisions, and authorization boundary in `objective.md`, `units.tsv`, `verdicts.tsv`, and `decisions.tsv`.
3. **Run one bounded owner per PR.** Use host collaboration tools when available, with exclusive branches or worktrees, exact file boundaries, acceptance criteria, and verification commands. Owners may build, test, push, and open or update PRs only as authorized. They invoke `$deepwright:unslop` and `$deepwright:no-comments` when available and triage automated review per `../references/bugbot-triage.md`. Otherwise execute sequentially.
4. **Verify at STACK-READY.** Each owner reports the exact head SHA. Invoke `$deepwright:swarm` for independent gates, live behavior through available host capabilities, and a receipts-and-diff audit that treats the PR body as untrusted. A blocked live check is not a clean verdict. Findings return to the owner. Apply [Shipping's review-validity rule](shipping.md) when the reviewed base, head, target, or patch changes; this does not authorize landing the stack.
5. **Append, never ship.** No owner merges, closes, or arms auto-merge. A clean verdict makes the PR eligible for the one linear chain in the order the user specified or dependencies require.
6. **Keep one topology writer.** Owners change only their branches and report head, base, and intended parent. The coordinator alone creates or retargets stack PRs through the selected GitHub backend. Only the root PR targets the resolved default branch; each child targets its parent branch. Prefer creating a fresh child branch from the parent and applying the verified commits. Rebasing or force-pushing an existing shared branch requires explicit authorization for that exact branch; verify the remote head immediately before `--force-with-lease`.
7. **Absorb drift and re-verify what changed.** Fetch the current default branch and process the chain bottom-up. A changed base or rebase rewrites descendants. Compare each PR's base, head, target, and stable patch ID, then refresh affected checks and independent review under [Shipping's review-validity rule](shipping.md). An unchanged patch ID does not preserve the verdict after its context changes. Do not rewrite a branch outside the named stack.
8. **Audit in bounded passes.** Drain collaborator results with host collaboration tools, update the run ledger, and checkpoint after each topology change. Use only wait and monitoring capabilities the host advertises. If the session ends, write `resume.md` with the next exact operation.
9. **Deliver the chain.** Return one verified bottom-to-top list with base and head SHAs. The user lands it. Do not merge or arm merge-when-ready from this playbook.

**Choosing between the autopilots.** Use Autopilot-full only when the user explicitly grants landing authority for named PRs. Use Autopilot-stack when work is dependent, the user wants review before landing, or merge authority is absent.

**Reply:** links to the stack root and tip, base and head SHA for each link, one-line verdicts, any branch rewrite authorization used, the run-ledger path, and anything parked with the reason.
